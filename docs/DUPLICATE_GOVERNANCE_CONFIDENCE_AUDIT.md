| 治理阶段 | 识别依据 | 可信度评级 | 处置动作 | 物理文件是否删除？ | 风险等级 |
|---|---|---|---|---|---|

## 二、Stage 1 (Byte-Hash) 的六重安全防护机制

为了确保在物理删除 185 首重复音频时具备“金融级”安全性，后端在代码实现中内置了 **六重熔断与防护网**：

```
┌────────────────────────────────────────────────────────────────────────┐
│                        Stage 1 物理安全防护流水线                         │
└────────────────────────────────────────────────────────────────────────┘
                                     │
                 [1. 散列门禁] 排除空值与 nohash 占位符
                                     ▼
                 [2. 择优算法] 计算 KeepScore，选出最优 Winner
                                     ▼
                 [3. 人工保护] IsProtected / 软删除曲目绝对豁免
                                     ▼
                 [4. 数据库事务] PostgreSQL 排他行锁与事务预提
                                     ▼
          ★ [5. 物理存在性双检] 尝试底层 SMB 打开并读取 Winner 文件
                   ├── 打开失败 ──► 🚨 立即熔断！整组跳过，绝对不删任何副本
                   └── 打开成功 ──► 允许执行底层 SMB 删除 Loser 文件
                                     ▼
                 [6. 孤儿记录] 物理删除失败写入 Manifest，支持幂等重试
```

### 1. 散列有效性门禁
- 仅处理有效的全局哈希，自动过滤空值、`nohash` 扫描占位符以及哈希未计算的条目。

### 2. 多维最优胜出者算法（KeepScore）
同一 Hash 分组内可能存在 2 份甚至多份文件，系统通过多维权重精准选出最值得保留的正本（Winner）：
- **音质与比特率（0~100 分）**：优先保留比特率更高、无损优先；
- **元数据丰富度（0~40 分）**：有真实专辑名（排除 `Unknown Album`）+20 分，有流派 +5 分，有年份 +5 分，有内嵌封面 +10 分；
- **权威身份挂载（+15 分）**：已建立 MusicBrainz 权威 MBID 身份者优先；
- **时效与路径清晰度（+5 分）**：规范整理目录（如 `NetDiskSync`）相比散落根目录优先保留。

### 3. 人工保护与软删除豁免
- 本次生产扫描中，共有 **74 首** 标记有人工保护（如用户收藏、人工打标、人工歌单）的曲目被直接豁免，绝不作为 Loser 清理。
- 之前标记为软删除（`IsDeleted = true`）的曲目自动排除在聚类之外，防止状态冲突。

### 4. 核心物理底线：Winner 物理存在性与可读性双检（Winner-Openable Verification）
这是本次更新加入的最硬核安全锁：
> **在通过 SMB 发送物理删除指令给任何重复副本前，系统必须首先通过 SMB 真实打开并读取胜出者（Winner）的文件流。**
> - 如果 Winner 文件因为磁盘损坏、路径断开、文件被锁等原因打不开，**整组删除操作立即中止，任何副本都不允许删除**！
> - 这彻底杜绝了“副本被物理删除了，结果正本其实也是坏的或不存在”的灾难。

### 5. 数据库事务排他与原子提交
- 数据库操作采用 `REPEATABLE READ` 隔离级别与原生行锁，单事务提交。
- 只有在数据库事务 Commit 成功后，才触发物理文件删除；若物理删除过程中网络中断，自动记录在 `rollbackManifest.PhysicalDeletion.FailedPaths` 中，支持后续一键二次重试或审计。

### 6. 云端独立冷备兜底
- MEDIA 服务器与 NAS 在执行前已完成全量备份并推送到百度网盘（`webmusic_full_pre_dedupe_20260912.sql.gz`），即使发生不可抗力，也可一键还原整个数据库。

## 四、为什么后续阶段（Stage 2 / 3 / 4）绝不物理删除？

正如您的指导原则，针对非 Hash 完全相同的曲目，目前坚决**不碰物理文件**，原因如下：

1. **同名但不同专辑版本（Stage 3 MBID 保护）**：
   - 比如同一首歌，在录音室专辑《范特西》有一版，在精选集《周杰伦十年精选》又有一版，在演唱会专辑《The One Live》又有一版。
   - 它们的 Recording MBID 可能相同，但对于音乐爱好者而言，**它们属于完全不同的收藏场景与专辑完整性，绝对不能当成“垃圾重复”删掉！**
   - 当前系统的防御规则：**只要专辑名称不同，一律排除在重复组之外，严格独立保留！**
2. **音质与压制格式差异（Stage 2 Exact Metadata）**：
   - 同名同时长，但一份是 320kbps MP3，另一份是 24bit FLAC。
   - 这属于“音质升级”或“跨格式”，需要更成熟的音频流合流算法，绝不能机械地直接把其中一个文件删掉。
3. **模糊匹配（Stage 4 Fuzzy）**：
   - 极易误伤现场版、Remix 版、Instrumental 伴奏版，当前策略仅作为报表输出，完全关闭自动删除。
